## Scheduling contract

An attempt is consumed when a lease and attempt row are committed, before HTTP starts.
Use the failed attempt number, not the number of future retries, to index the schedule.

| Failed attempt | Nominal wait before another attempt, if allowed |
|---|---|
| 1 | 10 seconds |
| 2 | 30 seconds |
| 3 | 2 minutes |
| 4 | 10 minutes |
| 5 | 30 minutes |
| 6 | 2 hours |
| 7 | 6 hours |
| 8–19 | 24 hours |

`max_attempts` defaults to 8, with a ceiling of 20. Check exhaustion before computing a next time:
failure on attempt 8 at the default is terminal, so it never schedules the 24-hour entry.
The seven nominal waits total **31,360 seconds (8h42m40s)**. This excludes HTTP duration,
dispatch delay, jitter and Retry-After; it is not a guaranteed completion deadline.

1. For a retryable result with attempts remaining, multiply the nominal wait by a uniform factor
   in [0.8, 1.2]. Inject the random source and clock in tests.
2. Parse Retry-After as nonnegative integer seconds or an HTTP date. Measure dates from the recorded
   completion time in UTC. A valid future header contributes a minimum wait capped at 24 hours.
3. Schedule using the larger of the jittered wait and the capped header wait. Jitter must never make
   a valid Retry-After request shorter. The cap applies to the header, not the jittered schedule.
4. Ignore negative, malformed, past-date and overflowing headers; use the policy wait and a bounded
   diagnostic reason. A zero header does not bypass backoff. Never persist raw headers in logs.
5. Persist the chosen `next_attempt_at` once with fenced completion. Duplicate completions and sweeps
   must not redraw jitter or extend an already scheduled retry.

`Retry-After: 3600` after failure 1 therefore waits one hour; after failure 7 the longer policy wait wins.
Success and non-retryable results ignore the header. Existing HTTP/IP/redirect protections remain.

## State, atomicity and recovery

- Close the attempt and update the event/dead-letter record in one PostgreSQL transaction under the
  M2 token, attempt-number and expiry fences. An expired worker cannot complete a newer lease.
- Persist a stable reason distinguishing attempts exhausted, non-retryable response and policy rejection.
  Keep status/error detail bounded and redact secrets. Specify exact reason identifiers before coding.
- An expired lease consumes its already claimed attempt. Recovery closes that attempt once and applies
  the same attempt budget; it must not create an extra uncounted HTTP attempt.
- Due-event publication may duplicate stream entries. PostgreSQL claim fencing prevents simultaneous
  delivery under one lease; destinations still need event-ID deduplication across leases.
- Run recovery and due-event scans in bounded batches with finite DB/Redis deadlines. Two concurrent
  sweepers cannot create duplicate attempts or terminal rows. PostgreSQL remains authoritative when
  Redis is flushed or unavailable; a publish error cannot discard durable work.
- Keep shutdown bounded and preserve pending work for the next process. No retention deletion in M3.

## Decisions to record before implementation

Write an M3 ADR covering repeated 24-hour entries, header/jitter precedence, terminal reason identifiers
and interrupted-attempt policy. Link it here and from the plan when accepted; do not edit accepted ADRs.
[ADR 0005](../adr/0005-m3-retry-policy.md) records these decisions and was accepted on 2026-11-15.
Resolve whether HTTP 410 disables an endpoint: the plan proposes it, but M2 and the future endpoint
management API must not be described as already doing so. Document any schema migration and defaults
for existing rows. Production schedule overrides need an explicit contract; do not invent environment
variables for a demo. Fast demos may use an injected test schedule.
